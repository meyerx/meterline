# Change list: meterline v2 spec v1.0

Findings from building `meterline-v2-SPEC-v1.0-2026-10-10.md`. The spec is frozen; each line is for the next version. A finding defaults to the code unless it says otherwise. Format: date, spec section, what was unclear or wrong, what the build did.

## Wording for the next version (2026-10-17)

Found by the review of 2026-10-15. None changes what the code does; the conventions are in `docs/dev/style.md`.

- §6.3 rule 5 · "not more than one year back" is a rolling window: `backfill` starts no earlier than 365 days before the pull day (`REPORT_DAYS_BACK` in `meterline_copilot/cli.py`). "Not more than 24 months back" counts calendar months: billing is read from the first day of the month 24 calendar months before the pull's month (`BILLING_MONTHS_BACK`, `_months_back`). The next version says both in those words.
- §2 and the Anthropic spec · "at most 365 days back" for `starting_at` is rolling too: a start day 365 or more days before the pull day is refused (`MAX_DAYS_BACK` in `meterline_anthropic/cli.py`), so at most 364 whole days before today.
- §6.4 rule 8 · "per UTC day d for which raw data exists" is unambiguous; the next version writes "that" ("each UTC day d that has raw data").
- §1 · The purpose sentence differs between the specs and the README. The next version opens with the README's first sentence, word for word.

### Findings

- 2026-10-11 · §3.1, §3.2 · Serialisation of `Decimal` values in `extras` is not stated (only `quantities` is "serialised as strings"). The build writes an integer as a JSON integer and a `Decimal` as a string without trailing zeros (as `quantities`), and reads both back; `cost` and `cost_list` keep v1's at-least-two-decimals text. The example `{"ai_credit": "12.5"}` is why quantities are not padded to two decimals.
- 2026-10-11 · §3.1 rule on cost vs §3.7 rule 3 · 3.1 says `currency` is `""` exactly when `cost` and `cost_list` are both null; 3.7 says exactly when `cost` is null. The two differ when only `cost_list` is set. The build follows 3.1 (currency describes whichever of the two is set). A cost row whose API currency is empty now fails validation in `meterline-anthropic` (v1 allowed it); the documented shapes always send a currency.
- 2026-10-11 · §3.7 rule 5 · Implemented as `meterline.actor_cost_failures(usage, org_totals)` over records, for the connectors of phases 2 and 3. `meterline-anthropic` keeps its v1 check on raw per-actor-day totals unchanged: with one provider, one scope, one grain and one basis the two are the same check, and the v1 unit test that drives it still holds.
- 2026-10-11 · §3.8 · `convert_v1_batch(path)` output name is not specified. The build writes `<name>.v2.jsonl` beside the v1 file and returns that path; the kind defaults to the name of the folder the v1 file is in.
- 2026-10-11 · §8 F02, A03 · "The v1.1 published fixture batches" did not exist as files; v1.1 only built them inside tests. The build generated them once with the v1.1 code on `main` (a `backfill --since 2026-10-01` at 2026-10-09 06:00 UTC, then a `daily` at 18:00 after one usage row changed) and committed raw files, run manifests and v1 records under `packages/meterline-anthropic/tests/fixtures/v1_published/`. F02 reads the v1 records from there (it lives in `packages/meterline`, the fixture in the connector's folder) and adds two hand-written v1 lines the fixture lacks (a cost-only row, a null cost with a deleted actor).
- 2026-10-11 · §8 A01 · A check that "all 17 v1.1 checks pass" cannot be a plain assertion: it runs the 16 checks of `test_done_check.py` and check 12 of `test_done_check_shapes.py` in a nested `pytest` and asserts `17 passed`. It roughly doubles those 17 checks' run time.
- 2026-10-11 · §3.1 grain · "window: any other range" is read as: a window must not be a single day or a whole calendar month (those are `day` and `month`), so a `grain=window` record with `period_start == period_end` is rejected.
- 2026-10-11 · §3.1 tokens · "when 5m and 1h are both non-null, they sum to `tokens_cache_write`" is applied literally: a record with both split fields set and `tokens_cache_write` null is rejected.
- 2026-10-11 · §10 · The spec names only some field names of the Cursor, OpenAI, Augment, Kiro and Windsurf sources. The build invented the rest in `docs/api-shapes/fit/` (for example Cursor's `totalTabsShown`, `acceptedLinesAdded`, `composerRequests`); they are synthetic and say so in that folder's README. Kiro's `Client_Type` goes to `scope`, so one user can have several records a day.
- 2026-10-11 · §4 · The run manifest's `totals` keys keep the raw-quantity names of v1 (`usage.tokens_input`, `usage.web_search_requests`, `activity.conversations`): they sum raw API values, not record fields, and the spec says the manifest keys keep their v1 names.
- 2026-10-11 · §3.5 · `SeatAssignment.period_start` must equal the UTC date of `pulled_at`; the build validates it, as the spec states the day is that date.
- 2026-10-11 · §3.8 · Review finding, documented not changed: `convert_v1_batch` writes `<name>.v2.jsonl` beside the v1 file, and a connector reads every `*.jsonl` of a kind's folder as v2, so an upgraded data directory must have its v1 files moved out and the `.v2.jsonl` files renamed (steps in `docs/records.md`). Spec says "beside"; writing to another folder would have been equally valid.
- 2026-10-11 · §3.1 · Review findings fixed: an integer in `quantities` is now written as a string like every quantity; a float in a field or map and a non-integer in `counters` are rejected by `validate`.
- 2026-10-11 · §3.1 · Review findings left, low: `from_dict` coerces `int(raw)` and `bool(raw)` without rejecting odd JSON types (a string `"false"` reads as true); Parquet writes `quantities` and `extras` as `decimal128(38, 10)`, so a value with more than 10 decimals would not fit. Neither is reachable from the connectors of this phase.

### Findings

- 2026-10-11 · §5.1 · The minimum LiteLLM version is resolved from the repository's tags: v1.67.0-stable. v1.66.0-stable lacks migration `20250415151647_add_cache_read_write_tokens_daily_spend_transactions`; v1.67.0-stable has it, the cache columns of `SpendMetrics`, `breakdown.entities` and `KeyMetadata.team_id`. The connector README and the 404 message name it.
- 2026-10-11 · §5.2 C · `/user/list` transcribed from v1.104.2: route `internal_user_endpoints.py` L2208-2378 (`get_users`), envelope `UserListResponse` (`types/proxy/management_endpoints/internal_user_endpoints.py` L31-40), user `LiteLLM_UserTableWithKeyCount` over `LiteLLM_UserTable` (`password` excluded). Sources named in `docs/api-shapes/litellm/README.md`.
- 2026-10-11 · §5.2 A, §5.4 · The user entities in `breakdown.entities` already carry `user_email` and `user_alias` in their metadata (`_resolve_user_email_metadata`), so `/user/list` is not needed for emails. The build follows the spec (reads C once per run); reading the entity metadata would save the call. Next version may drop C.
- 2026-10-11 · §5.4 rules 4 and 9 · The proxy counts a raw row with a null model in the day's `metrics` but skips it in `breakdown.models`. Taken literally, rule 4 (per date and model) would lose that usage and rule 9 (totals equal the global `metrics`) would fail. The build treats "metrics minus the sum of the model rows" as a bucket with `model` `""` in every view; per-user usage of it becomes `proxy_user` records with `model` `""`, and the unassigned difference is derived on that bucket too. `OrgTotal` stays per-model only (3.6: never per-model and all-models rows together), so the day's `OrgTotal` models can add up to less than the global cost; the manifest lists such dates under `modelless_days`.
- 2026-10-11 · §3.7 rule 5 · Because of the row above, the actor-cost check of the LiteLLM run compares each actor's day cost with the global view's `spend` for that day rather than with the `OrgTotal` sum (which can omit model-less spend).
- 2026-10-11 · §5.3 rule 3 · "Every closed UTC day since the last loaded day, and always the two days before the pull day" is read as `start = min(last loaded + 1, today - 2)` through yesterday; with nothing loaded, `daily` starts at the first of the current month (as in v1), and no further back.
- 2026-10-11 · §5.4 rule 7 · "Ended at least 2 full UTC days before `pulled_at`" is read as `pulled_at >= midnight(day + 1) + 2 days`. The two days re-read by `daily` are therefore never final.
- 2026-10-11 · §5.3 rule 1 · An end-user id that contains a comma cannot be asked for alone (the route splits `end_user_ids` on commas). The build skips such ids and counts them in the manifest under `skipped_entities.ids_with_comma`.
- 2026-10-11 · §5.3 · The httpx and httpcore loggers log every request URL at INFO, and a LiteLLM URL carries a user id (which may be an email). The CLI sets those loggers to WARNING; a test checks the logs and manifests for ids.
- 2026-10-11 · §5.4 rule 2 / manifest · `token_anomalies` entries are `<date>|<model>|<actor_kind>|<12 hex of sha256(actor id)>`, not the actor id: a LiteLLM user id can be an email, and logs and manifests carry no emails.
- 2026-10-11 · §5.2 · Optional metrics: when `SpendMetrics` omits `cache_read_input_tokens` or `cache_creation_input_tokens`, `tokens_input_uncached` is null (it cannot be split) while `tokens_input_total` is kept.

### Review of phase 2 (independent reviewer, 2026-10-11)

- 2026-10-11 · §5.4 rules 4 and 9 · Review finding, fixed: LiteLLM adds `spend` as binary floating point in a different order for the day, the models and the users, so the sums differ by about 1e-16; exact `Decimal` comparison would fail runs or write phantom model-less records. The build treats a money difference below 0.000001 as zero in the model-less bucket, the unassigned difference, rule 9 and the actor-cost check. Counts stay exact. Spec 5.4 should say so; "to the cent" in L04 already implies it. Cost values keep the digits the proxy sent (for example `0.30000000000000004`); the spec does not ask for rounding.
- 2026-10-11 · §3.8, v1.1 check 9 · Review finding, fixed in `meterline-litellm`: `pulled_at` with microseconds was written in full to records but cut to whole seconds in the run manifest, so a rebuild would differ. The connector now truncates `pulled_at` to whole seconds. Not fixed, out of this phase: `meterline-anthropic` reads `now()` the same way and by reading its code has the same latent difference (its tests use whole-second times). Candidate for a small fix in the next version.
- 2026-10-11 · §5.3 rule 3 with §5.4 rule 7 · Review finding, spec inconsistency, not changed: `daily` re-reads the two days before the pull day, and a day is final only from the third day after it. A day read last at pull day D+2 is never read again, so `daily` alone never writes `is_final = true` for it; only `backfill` does. A reader that needs final data should wait for a `backfill` over the period, or the next version should re-read three days.
- 2026-10-11 · §5.4 · Review finding, left, low: a key that disappears on a re-read (an `unassigned` difference that falls to 0 because late rows were re-attributed to a user) writes no replacement, so the earlier record stays the latest for its key. LiteLLM rows are normally immutable; v1 had the same property. Listed in the connector README under known limits.
- 2026-10-11 · §8 L02, L05 · Review finding: L02 splits a day across pages but no single model across them, and one assertion in L05 cannot fail. Checks are not edited after they were shown to fail; two added tests cover both (`test_a_model_split_across_pages_is_summed`, `test_end_users_never_change_the_unassigned_records`).
- 2026-10-11 · §5.1 · Review findings, fixed: a user name or password in `LITELLM_BASE_URL` is dropped (the bearer key is the only credential sent, and the stored request URL never holds one); a response body that breaks the documented shape (a string where a number belongs, a view and date twice) now ends the run with exit 2, a failed manifest and nothing published, not a traceback.
- 2026-10-11 · §5.2 · Review finding, rejected: hashed ids in file names and manifest entries could be guessed from a list of known emails. Kept: they are for telling entries apart, not for secrecy, and the raw files hold the ids anyway.

### Findings

- 2026-10-11 · §6.2 B · The aggregate row of a `*-1-day` report was transcribed from https://docs.github.com/en/copilot/reference/copilot-usage-metrics/example-schema, section "Enterprise-level schema example". That example is a 28-day report with the aggregate inside a `day_totals` array; the page shows no one-day row and no organization-level aggregate example. The shape file pins that layout with one `day_totals` entry for the requested day. The normaliser reads the three active-user counts from the `day_totals` entry whose `day` is the requested day and falls back to the top level of the row.
- 2026-10-11 · §8 C11 · The check as first written (and shown failing) asserted that the two waits add up to 7 + 40 seconds. `x-ratelimit-reset` is an absolute time, scripted 40 seconds after the start, so the 7-second wait already counts toward it and the honest total is 40. The assertion was corrected to what the text says: the `retry-after` wait comes first, then the clock reaches the reset time before the retry. Same intent, corrected arithmetic; the check stays strict (it still fails on an immediate retry).
- 2026-10-11 · §8 C01 · The fake's aggregate row lacked the optional-looking fields of the documented `day_totals` entry (`distinct_*_use_count`, the `totals_by_*` arrays); the check reported them missing. The fake (test data), not the check, was changed to carry the documented entry in full.

### Review of phase 3 (independent reviewer, 2026-10-11)

- 2026-10-11 · §3.6, §6.4 rule 7 · Review finding, fixed: one billing item with an empty or missing `model` next to per-model items of the same product made the batch fail ("org-total periods mix per-model rows with an all-models row") and, at the day level, repeated for four days. The build writes the model-less group of such a day and product under the model `(no model)`; with no per-model item it stays `""`. Spec should say what a model-less item is.
- 2026-10-11 · §6.3 rule 1, §6.4 rule 10 · Review finding, spec inconsistency, not changed: `daily` re-reads four days and a day is final only from the fifth day after it, so a day record written only by `daily` stays `is_final = false`; the organization's billing records (final a week after month end) are never re-read that late by `daily` either. `backfill` over the period writes the final ones. Next version: re-read five days, and re-read the month's billing days until the month is final.
- 2026-10-11 · §6.4 rule 5 · Unlogged deviations found by review, now logged: `price_per_unit` is kept in `extras` only when every merged item has the same price (spec: always present); a missing `discountQuantity` or `netQuantity` counts as 0; unit names that are not letter-led get a `unit_` prefix.
- 2026-10-11 · §6.1 · `x-ratelimit-reset` is waited out on a 429 or when `x-ratelimit-remaining` is 0, not on every 403 that carries it (GitHub sends the header on ordinary 403s); a 403 with neither `retry-after` nor an exhausted limit is a permission error and fails at once.
- 2026-10-11 · §6.2 A · A report row dated outside its report day, or without a whole-number `user_id`, fails the run with exit 2 (the spec is silent).
- 2026-10-11 · §7 · `tests/fixtures/` does not exist: the synthetic rows live in `tests/copilot_fake_api.py`. The C12 scan covers the folder if it appears.
- 2026-10-11 · §6.3 · Review finding, fixed: a data directory is now bound to the `org_id` of its first run (`state.json`); a run for another organization or level in the same directory exits 2 instead of mixing logins and loaded days. Also fixed: `month_people` is computed once per month in the normaliser (it was once per person); a non-finite `retry-after` or `x-ratelimit-reset` is ignored.
- 2026-10-11 · §2 · Review findings, left, low: `pending` fetch steps never expire (a failed run resumed days later reuses its raw files under the new `pulled_at`; a different command in between drops them); a checks failure clears `pending`, so a failed 365-day backfill refetches; the hashes of logins and ids in file names and manifests are not secrecy, only absence of the plain value.

### Review fixes, 2026-10-16

- 2026-10-17 · §9 · F-44, deviation by owner decision: the mapping to the standards moves to `docs/standards-mapping.md`, which maps every field of the five record types, cites FOCUS 1.4 and the OpenTelemetry GenAI conventions at a fixed commit with the date checked, and sets a review-by date. It departs from the section 9 table on three points: a cost whose `cost_basis` is `consumption` or `estimate` is not `EffectiveCost` (it goes to a custom column), `cost_list` is an approximation of `ListCost`, and `model` maps to a tag, not `SkuId`.
- 2026-10-16 · §5.2 · F-06, deviation by owner decision: the spec says "a missing metric reads as not reported (null)". `meterline-litellm` now fails the run (exit 2, failed manifest, nothing published, message `user_daily_activity: metrics.<name> is missing`) when any of the nine `SpendMetrics` it reads is absent, null, a string, a bool or not finite, because a supported proxy (v1.67.0-stable or later) always sends them and a silent null undercounts. Also required: the `date` and `metrics` of each result and the `user_id` of each `user_list` entry.
- 2026-10-16 · §6.4 rule 1, §6.2 · F-06, deviation by owner decision: the spec writes the daily credits record "only when `ai_credits_used` is present". `meterline-copilot` now fails the run (exit 2, failed manifest, nothing published, message `users_1_day <day>: ai_credits_used is missing`) when a report row lacks it or sends it as null, a string, a bool or a non-finite number. Likewise required: `token_usage.prompt_tokens_sum`, `token_usage.output_tokens_sum` and `request_count` of a `totals_by_cli` or `totals_by_copilot_app` block that is present (the blocks themselves stay optional), and the six quantity and amount fields of every billing item (`discountAmount`, `discountQuantity` and `netQuantity` no longer default to 0). Risk to watch: if GitHub omits `ai_credits_used` for some historical period, a `backfill` over that period fails until the code names a floor date.
- 2026-10-16 · §5.3, §6.3 · F-11, deviation by owner decision (both connectors): with no `state.json`, `daily` used to start at the first day of the current month; `meterline-litellm` and `meterline-copilot` now stop with exit 2 and a message, and ask for the new option `--since YYYY-MM-DD` (the first day to load; a warning names it). A fresh data directory needs it on the first run; once a state file exists `--since` is ignored with a note. A damaged `state.json` (cut short, empty, wrong shape, a path outside the data directory) stops `backfill` and `daily` with exit 2, names the file and the recovery step, and changes nothing.
- 2026-10-16 · §5.3, §6.1 · F-41: LiteLLM stops with exit 2 when a page repeats the one before, the answer names a page other than the one asked for, or a query passes 10,000 pages (it was 100,000 and an exit-1 error). Copilot stops with exit 2 on a repeated seat page, on seat pages that hold fewer distinct people than `total_seats`, on a download link listed twice and on two links that give the same file; the seat cap is 10,000 pages (was 100,000). In all three connectors a `Retry-After` wait is capped at 300 seconds (`--max-retry-after`) and both RFC 9110 forms are read; Copilot's cap on `x-ratelimit-reset` stays 7,200 seconds. Not done: a Copilot report whose download link is left out cannot be seen from the client.
- 2026-10-16 · §5, §6 · F-26 (LiteLLM and Copilot): same as the Anthropic connector. A raw file is never replaced; a second pull in the same UTC second stops with exit 2 and no manifest, and a run starting in the second of a finished run is refused before any request. The retention rule is in each README.

- 2026-10-17 · §5.3, §6.1 · F-48: the throttle, back-off and `Retry-After` code of the three connectors now lives once, in `meterline.http`, and one test suite (`packages/meterline/tests/test_http_connectors.py`) runs the same cases against all three. ### Pre-publication review, batch 1 (connector correctness), 2026-10-30

From the pre-publication review at c246df2 (findings MF-1 to MF-3 and the connector items); each entry was reproduced by a test that failed before the change.

- 2026-10-30 · MF-2 · decision records 0001 and 0006 say Parquet amounts are `decimal128(38, 10)` and that a value with more decimals does not fit. A real LiteLLM spend is a float with 15 to 19 decimals: the connector kept every digit, the gold build refused more than 12 (exit 2) and `--parquet` died on an uncaught ArrowInvalid. Changed: the core owns one scale, `MAX_DECIMALS = 12`; `validate` refuses more, Parquet writes `decimal128(38, 12)`, gold imports the constant, and the LiteLLM connector rounds `spend` and `flat_cost` to 12 decimals (half to even) at read. - 2026-10-30 · B1-c · `meterline.http.mask` replaced secrets in the order given, so `mask('abc-longsecret-xyz abc', ['abc', 'abc-longsecret'])` left the tail of the longer secret. Changed: longest secret first.
- 2026-10-30 · MF-3 · a 200 answer without its envelope (`data`, `results`, `metadata`) gave exit 0 with no records and recorded the days as loaded, so `daily` never asked for them again (anthropic, litellm; admin already refused a missing `data` or `results`, but recorded every day of an empty answer as loaded); a missing `actor.email_address` gave a null e-mail. Changed: a missing or null envelope key is a named error (exit 2, nothing loaded); a day with no rows is recorded as loaded only once it is final (anthropic: its month ended more than 7 days ago; admin: 48 hours after the day; litellm: two full days), and the run manifest counts those days under `empty_days`; anthropic `daily` now starts the seat-summary request after the latest loaded summary day (it asked only for yesterday), and an open empty day keeps itself and the days after it out of the activity and summary lists so that `daily` comes back to it; `actor.email_address` (and `user.email_address` in `users`) must be present, null stays allowed. - 2026-10-30 · B1-d · a write-phase `OSError` (disk full, permission) escaped `run()` in all four connectors and left a published batch file with no manifest; `resume` healed it but "a failed run does not raise" was false. Changed: one helper in the core, `meterline.run.WritePhase`, wraps the record files, the manifest and the state write of a run; on an `OSError` it removes the files of that batch, prints a plain message, and the connector returns exit 1 (transient, retry). The state file is written last and atomically, so it is unchanged and the next run reuses the pending raw files and publishes the clean result.
